# File storage, documents and proof of delivery (Phase 10)

This document covers file storage, the Media Library, private documents, secure access, the proof-of-delivery (POD)
workflow, the API, security, configuration and what is **not** done. Related: `CMS.md` (website media),
`SUPER_ADMIN_PANEL.md`, `CARRIER_PORTAL.md`, `CUSTOMER_PORTAL.md`.

## 1. What exists

| Area | Behaviour |
| --- | --- |
| Storage layer | One provider abstraction (`backend/src/storage`): `upload`, `delete`, `getMetadata`, `createSecureAccess`, `exists`. Controllers never name a provider. |
| Providers | `cloudinary` (production), `local` (development only, refused in production), `memory` (automated tests only). |
| Media Library | `/admin/cms/media`: upload, list, search, filter, pagination, preview, metadata, edit, replace, archive/restore. **Public** website media. |
| Documents | Private business documents (BOL, POD, rate confirmation, W9, insurance, invoice, other) with owner-based access. **Never public.** |
| Secure access | Authorization first, then a short-lived link generated by the server. Links are never stored. |
| POD | The carrier uploads proof of delivery from their own shipment; the customer and the Super Admin can open it. Replacement is explicit and archives the old one. |

Without credentials nothing crashes and nothing pretends to work: every upload answers **`501 STORAGE_NOT_CONFIGURED`**
("File storage is not configured yet.") and each screen says the same. Setting the variables below turns uploads on with no
code change.

## 2. Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `STORAGE_PROVIDER` | empty | `cloudinary` or `local`. Empty = Cloudinary when all three `CLOUDINARY_*` values exist, otherwise no storage. |
| `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | empty | Server-side only. Never returned by any API, never logged, never put in the audit trail. |
| `STORAGE_LOCAL_DIR` | `storage-data` | Folder for the `local` provider (git-ignored). |
| `API_PUBLIC_URL` | `http://localhost:PORT` | Public base URL of the API, used to build `local` links. |
| `STORAGE_SIGNED_URL_TTL_SECONDS` | `300` | Lifetime of a private-file link (30-3600). |
| `UPLOAD_IMAGE_MAX_MB` / `UPLOAD_VIDEO_MAX_MB` / `UPLOAD_DOCUMENT_MAX_MB` | `10` / `200` / `25` | Size limits. |

`STORAGE_PROVIDER=local` together with `NODE_ENV=production` fails at startup.

### Setting up Cloudinary

1. Create a Cloudinary account and copy the cloud name, API key and API secret from the dashboard.
2. Set the three `CLOUDINARY_*` variables on the API host (a secret store, not the repository). Restart the API.
3. Open `/admin/cms/media`: the page now says "File uploads are available" and shows the limits. `GET /admin/cms/media/storage`
   returns `{configured, provider, uploadsAvailable, limits, message}` and nothing secret.
4. In Cloudinary, keep private documents on the **authenticated** delivery type (the driver already uploads them that way)
   and leave "Strict transformations" on.

> **The Cloudinary driver is not verified against a live account.** It is a small REST client that signs requests the way
> the Cloudinary documentation describes and is tested with a mocked `fetch`. Real Cloudinary integration was not tested
> because storage credentials were not configured. Before relying on it, upload one image, one PDF, open a private PDF
> through the app and download it. The exact shape of the private-file download link is the most likely thing to need a
> tweak, and it is isolated in `cloudinary.driver.js`.

## 3. Public media vs private documents

* **Media** (`Media` model) is for the website. It is stored with public access and has a stable public URL that CMS pages
  can use. It carries only safe metadata.
* **Documents** (`Document` model) are private. They are stored with private access (`authenticated` in Cloudinary,
  `private/` on disk), have no public URL, and are only reachable through an authorized endpoint that returns an expiring
  link. A document cannot be turned into media and vice versa.

## 4. Upload handling

Each request carries exactly one file as the **raw request body**. The file's type is the `Content-Type`; its name and the
few allowed fields travel in a strict query string (unknown keys, `$` operators and owner/storage fields are a 400). There is
no multipart parser and no extra dependency.

Order of checks: authentication/role -> storage configured (501 otherwise) -> query validation -> declared content type (415)
-> `Content-Length` and a byte counter against the size limit (413 `FILE_TOO_LARGE`) -> content inspection -> ownership of the
related record -> upload -> database write. If the database write fails after the file was stored, the stored file is removed
again (cleanup); if cleanup itself fails the error is logged without the key.

**Content inspection** (`fileValidation.js`) never trusts the browser:

* the extension must be allowed for the declared type (double extensions such as `photo.png.php` are refused);
* the real signature must match: JPEG, PNG, GIF, WebP, PDF, MP4 (HEIC-family brands excluded), WebM;
* HTML, script, PHP and shell content is refused even if the extension and type look fine;
* image width/height and video duration are read from the file itself;
* exe, bat, cmd, sh, scripts, SVG, HTML, PHP and unknown binaries are rejected (415 `UNSUPPORTED_FILE_TYPE`; a body that does
  not match its declared type is 422 `FILE_CONTENT_MISMATCH`; an empty body is 400).

| Purpose | Allowed | Limit |
| --- | --- | --- |
| Website media | JPEG, PNG, WebP, GIF, MP4, WebM | images 10 MB, video 200 MB |
| Documents / POD | PDF, JPEG, PNG, WebP | 25 MB |

File names are display values only: they are sanitised and **never used as a storage path**. Storage keys are random
(`<access>/<folder>/<uuid>.<ext>`).

## 5. API

Envelope `{success, data, message}`. Foreign records are always **404**, never 403.

### Super Admin (`authenticate` + `requireSuperAdmin`)

| Route | Notes |
| --- | --- |
| `GET /admin/cms/media/storage` | provider status and limits (no secrets) |
| `POST /admin/cms/media/upload?fileName=&folder=&altText=&caption=` | raw body |
| `POST /admin/cms/media/:id/replace?fileName=` | new file stored first; old object kept; `previousVersions` recorded (max 10) |
| `GET/PATCH /admin/cms/media/:id`, `POST .../archive`, `.../restore` | metadata only |
| `POST /admin/documents?fileName=&type=&relatedEntityType=&relatedEntityId=&visibility=&name=` | raw body |
| `GET /admin/documents`, `GET /admin/documents/:id` | filters: q, type, status, visibility, related type, customerId, carrierId, shipmentId, loadId, uploadedBy, createdFrom/To, archived |
| `GET /admin/documents/:id/download?disposition=inline\|attachment` | returns `{access:{url,expiresAt,expiresInSeconds,disposition,fileName,mimeType}}` |
| `PATCH /admin/documents/:id` | name, type, visibility, or move to another record |
| `POST /admin/documents/:id/archive`, `/restore` | never deletes the file |

### Carrier

| Route | Notes |
| --- | --- |
| `POST /carrier/shipments/:id/pod?fileName=&replace=true|false` | proof of delivery |
| `POST /carrier/shipments/:id/documents?fileName=&type=BOL\|Other&name=` | supporting document, carrier-visible only |
| `GET /carrier/documents`, `/:id`, `/:id/download` | own, carrier-visible documents only |

### Customer

`GET /customer/documents`, `/:id`, `/:id/download` - own, customer-visible documents only. Customers cannot upload.

### Local provider (development only)

`GET /storage/local/f/:token` (private files; HMAC-signed, expiring token) and `GET /storage/local/p/:folder/:file`
(public media). Both answer 404 unless the local provider is active, and there is no way to request a file by path.

## 6. Ownership and visibility

Identity always comes from the session. The server **never trusts** a client `customerId`, `carrierId`, `shipmentId`, `loadId`,
`ownerId`, `uploadedBy` or `storageKey`: they are rejected as unknown query keys (400). For uploads, the related record is
looked up and the customer and carrier are **derived from it**. Visibilities: `private`/`admin` (Super Admin only),
`customer`, `carrier`, `shared` (customer and carrier). A customer sees `customer`+`shared`, a carrier sees `carrier`+`shared`,
and only their own, non-archived records. A visibility that cannot apply to the record (for example `carrier` on a record that
has no carrier) is a 422.

Carriers and customers never see each other's identity, pricing or margin: document payloads contain no partner id or name,
no rates and no storage references (tests assert this).

## 7. Secure access

1. Authenticate and apply the role's ownership filter (a foreign or archived document is a 404 before any link exists).
2. A record without a stored file, or stored by a provider that is not the configured one, answers
   `501 DOWNLOAD_UNAVAILABLE`; no provider at all answers `501 STORAGE_NOT_CONFIGURED`.
3. The provider creates an expiring link (default 5 minutes). It is returned in the response and **not stored** in the
   database, the audit log or the logs. Every request asks again.
4. `document.downloaded` / `document.previewed` is written to the audit trail with the document id and the user, never the link.

A missing stored object is 404 `STORAGE_FILE_MISSING`; provider errors become a generic 502/503 with no provider text.

## 8. Proof of delivery

* Only the carrier assigned to the shipment can upload, and only while the shipment is **out for delivery, delivered or
  completed**. Cancelled, archived, unrelated or not-yet-delivering shipments are refused (409 `POD_NOT_ALLOWED_YET` or 404).
  The shipment state machine is not changed: a POD upload never changes the shipment status.
* A POD is stored privately with visibility `shared` and `isPrimary`. The customer, the carrier and the Super Admin can open it.
* A second upload without `replace=true` is **409 `POD_ALREADY_EXISTS`**; nothing is overwritten silently.
* `replace=true` creates the new primary POD (linked through `replacesDocumentId`), **archives** the previous POD (its stored
  file is kept) and writes `document.pod_replaced` and `document.archived` audit entries.
* The customer and the Super Admin get an in-app notification; the text names the tracking number, never the carrier.
  Phase 11: the same notification is also queued as an email (and an SMS if the recipient opted in) when a provider is configured.
* The Super Admin shipment page shows "Proof of delivery: on file" from the real document.

## 9. Audit

`media.uploaded`, `media.replaced`, `media.archived/restored`, `document.uploaded`, `document.updated`,
`document.archived/restored`, `document.pod_uploaded`, `document.pod_replaced`, `document.downloaded`, `document.previewed`.
Entries hold ids, types and counts only - never a signed link, a storage key or a secret (the audit model also rejects
secret-looking metadata keys).

## 11. Known limitations

* **Real Cloudinary integration is untested** (see section 2). The local provider is for development only.
* **No malware scanning.** Validation checks type and structure, not whether a PDF or image is harmful.
* **No retention or cleanup policy.** Archiving, replacing and a failed move never delete stored files; nothing removes them
  later. Add a retention job once a policy exists.
* Media replace does not rewrite addresses already copied into CMS content.
* Files are buffered in memory while validating (up to 200 MB for a video), so very large videos need a larger instance;
  direct-to-provider uploads would be the next step.
* Two POD uploads at exactly the same moment could create two primary PODs (no transaction); the admin can archive one.
* Preview needs the browser to allow the provider's frame (`frame-ancestors` is set for `CLIENT_URL` on the local provider; check the
  Cloudinary equivalent when it is connected).
* Email/SMS arrived in Phase 11 (see `docs/NOTIFICATIONS_AND_MESSAGING.md`); no payments. Tested on FerretDB, not a real MongoDB.
